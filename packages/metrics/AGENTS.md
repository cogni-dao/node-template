# metrics

Published @cogni-dao/metrics owns contracts, calculator registry, bounded computation, evidence selection and injected observation adapters.

Public surface: `.` (engine, registry, assessment, goal-progress read model), `./contracts` (wire schemas), `./adapters/postgres` (observation store over an injected `postgres` client), `./schema` (table definitions), `./briefs` (pure `brief-rules@1` scorer: `scoreBrief`, `summarizeBriefs`, `briefEvidenceRefs`, `fieldSentences`, the rule lists and limits), `./sources` (node-agnostic readers: `readWorkCount`, `readWorkConvergence`, `readWorkValidatedHistory`, `readGithubStars`, `readBriefConformance`, `briefConformanceSql`, `BRIEF_MAX_ROWS`, `BRIEF_MAX_BYTES`, `doltInstant`, `FIRST_PARENT_WALK_CAP`, `RECORDED_HEAD_MAX_GAP_SECONDS`, `MAIN_HEAD_EVIDENCE_PREFIX`, type `RecordedMainHeads`) and `./knowledge` (`createGoalMetrics`, `createGoalSource`, `createGoalProgressReader`, `GoalKnowledgeReader`, `PACKAGE_CALCULATOR_IDS`, `RESERVED_CALCULATOR_FAMILIES`, `calculatorFamily`, `BUILTIN_METRICS`, `BUILTIN_METRIC_REVISION`).

No app, knowledge-store, Temporal, environment, migration or pool lifecycle imports. `./knowledge` takes SQL clients, node id, environment, log sink and a structural `GoalKnowledgeReader` (satisfied by `KnowledgeStorePort`) as arguments. `./schema` exports table definitions only (optional `drizzle-orm` peer) plus `METRIC_FORCE_RLS_SQL`; each node re-exports it from its db-schema and generates its own migrations. Nodes own node identity, clients and credentials, migrations, routes, refresh scheduling, UI and DI composition. Calculator ids, budgets, evidenceRefs strings, log event names and the source allow-list are a published contract: changing any is a version bump. Root and adapter share typed errors. Every `work.convergence@1` reading records main's head as `dolt:head:<hash>@<iso>`; window edges resolve reflog, then the newest stored ok head within `RECORDED_HEAD_MAX_GAP_SECONDS` (`PostgresMetricObservations.recordedMainHead`), then the capped first-parent walk. Preserve units, immutable completed observations, request snapshots, fencing, source coverage, and unknown results. Prove packed JavaScript and declarations in a clean consumer.

Display (0.3.0): a calculator declares how its readings read best (`display` or `displayFor(params)`: `progress`, `volume`, `slo`); a metric definition may override it in `metric_spec.display`, parsed strictly by `StoredMetricSpecSchema` and kept outside the series hash. `slo` needs unit `%` (`displayFits`); an override the unit cannot honour yields to the calculator default. Every goal KPI carries the resolved `metric.display`, its 30 daily `trend`, and `recent` (last 24 hourly buckets) when the metric refreshes hourly or faster. Readers must not infer display from units.

Node calculators (0.4.0): `createGoalMetrics({ nodeCalculators })` registers calculators over sources only that node owns (for example the operator's release tables; ids match `MetricSpecSchema.calculatorId`, so `deploy.release-success@1`, never an underscore) after the package calculators and admits them in the same `node-members` scope. A node calculator may not use a published family (`work.count`, `work.convergence`, `github.stars`) at any version (`reserved_calculator_family`; `RESERVED_CALCULATOR_FAMILIES`), so the package keeps every future version of its own ids; nodes name theirs in their own families (for example `deploy.*`, `node.*`). Two node calculators cannot share an id (`duplicate_calculator`). The service enforces each node calculator's `timeoutMs` and `maxSourceCalls` exactly as for built-ins; sources must honour `maxRows` and `maxResponseBytes`. An id the spec schema rejects throws `invalid_calculator_id`, and a definition naming an unregistered calculator stays `metric_not_found`. The package contract above covers only `PACKAGE_CALCULATOR_IDS`; each node owns and versions its own calculators. A calculator that reads private connection data must not be injected here until it carries its own grant check.

`brief.conformance@1` (params `{subject: items|entries, maxLongShare 0..0.5}`, unit `%`, one source call, 5000 rows, 16 MiB, 15 s) scores open work items or live hub entries with `brief-rules@1`; the value is the share that pass every agent-fixable rule, and rows that break only the human-gated `Goal =` rules stay counted and pass (`human_gated_failing=K` in evidence). The two built-in definitions `brief-conformance-items` and `brief-conformance-entries` (revision `builtin:brief-rules@1`, cadence 3600 s, max age 7200 s) are served by `definitions.get` and `list` beside hub rows: a hub row of the same id wins in any status, a deprecated or invalid one never falls back (logs `metric.definition_invalid`), and `list` merges one hub page with the built-ins by id. Any change to a rule, list, limit, built-in spec or evidence string is a version bump. The terminal `metric.compute.completed` event carries `reason`. Doltgres 0.57.3: `octet_length` panics on stored long text unless wrapped in `substr`, and a bare `SUM` compares as text, so the statement casts it to `BIGINT`.

Breach (0.6.0): a KPI binding may set `breach: "failing"`. Before the deadline, a fresh good reading that misses the comparator is then `failing` with reason `target_breached` instead of `behind`. A stale reading stays `delayed`, a failed attempt keeps its own reason, and after the deadline `met` / `missed` is unchanged. Without the field nothing changes. A reader on a package older than 0.6.0 rejects a binding that carries the field (strict schema), so upgrade readers before any goal row sets it.

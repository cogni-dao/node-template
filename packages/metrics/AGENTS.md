# metrics

Published @cogni-dao/metrics owns contracts, calculator registry, bounded computation, evidence selection and injected observation adapters.

Work projections use `workReadBatch` and `predictionBatch`: scoped batched reads reauthorize current and pinned definitions and retain immutable due observation identity. Batch support is optional on injected ports and fails closed when unavailable. Fixed predictions discover pinned snapshots, authorize their definitions and derive calculator/parameter/unit/window constraints before the bounded due selector chooses a winner. Direct selection uses the same constraints; missing constraints select no due evidence. Goal-progress reads remain serial for reserved ports; the node opts its pooled read port into at most two concurrent goals, preserving full ordered output and awaiting native sibling settlement.

Public surface: `.` (engine, registry, assessment, goal-progress read model), `./contracts` (wire schemas), `./adapters/postgres` (observation store over an injected `postgres` client), `./schema` (table definitions), `./briefs` (pure `brief-rules@1` scorer: `scoreBrief`, `summarizeBriefs`, `briefEvidenceRefs`, `fieldSentences`, `toLines`, the rule lists and limits), `./no-inline-history` (pure `no-inline-history-rules@1` marker scorer: `markerLines`, `scoreNoInlineHistory`, `passesNoInlineHistory`, `approvedLines`, `appendsHistory`, `summarizeNoInlineHistory`, `noInlineHistoryEvidenceRefs`, `NO_INLINE_HISTORY_RULES`, `NO_INLINE_HISTORY_RULES_VERSION`, `NO_INLINE_HISTORY_FIELDS`, `NO_INLINE_HISTORY_MAX_FIELD_CHARS`), `./sources` (node-agnostic readers: `readWorkCount`, `readWorkConvergence`, `readWorkValidatedHistory`, `readGithubStars`, `readBriefConformance`, `briefConformanceSql`, `BRIEF_MAX_ROWS`, `BRIEF_MAX_BYTES`, `readNoInlineHistoryState`, `readNoInlineHistoryScope`, `readNoInlineHistoryEdits`, `noInlineHistoryStateSql`, `noInlineHistoryWindowCommitsSql`, `noInlineHistoryEditsSql` (takes the window's commit hashes), `NO_INLINE_HISTORY_MAX_ROWS`, `NO_INLINE_HISTORY_MAX_BYTES`, `NO_INLINE_HISTORY_MAX_EDITS`, `NO_INLINE_HISTORY_MIN_EDITS`, `doltInstant`, `FIRST_PARENT_WALK_CAP`, `RECORDED_HEAD_MAX_GAP_SECONDS`, `MAIN_HEAD_EVIDENCE_PREFIX`, type `RecordedMainHeads`), `./http` (framework-neutral `/api/v1/metrics/*` route core: `createMetricHttpHandlers`, `metricErrorResult`, `METRIC_HTTP_HEADERS`, types `MetricHttpResult`, `MetricHttpPorts`, `MetricRouteService`, `MetricSubjectRow`) and `./knowledge` (`createGoalMetrics`, `createGoalSource`, `createGoalProgressReader`, `GoalKnowledgeReader`, `PACKAGE_CALCULATOR_IDS`, `RESERVED_CALCULATOR_FAMILIES`, `calculatorFamily`).

No app, knowledge-store, Temporal, environment, migration or pool lifecycle imports. `./knowledge` takes SQL clients, node id, environment, log sink and a structural `GoalKnowledgeReader` (satisfied by `KnowledgeStorePort`) as arguments. `./schema` exports table definitions only (optional `drizzle-orm` peer) plus `METRIC_FORCE_RLS_SQL`; each node re-exports it from its db-schema and generates its own migrations. Nodes own node identity, clients and credentials, migrations, routes, refresh scheduling, UI and DI composition. Calculator ids, budgets, evidenceRefs strings, log event names and the source allow-list are a published contract: changing any is a version bump. Root and adapter share typed errors. Every `work.convergence@1` reading records main's head as `dolt:head:<hash>@<iso>`; window edges resolve reflog, then the newest stored ok head within `RECORDED_HEAD_MAX_GAP_SECONDS` (`PostgresMetricObservations.recordedMainHead`), then the capped first-parent walk. Preserve units, immutable completed observations, request snapshots, fencing, source coverage, and unknown results. Prove packed JavaScript and declarations in a clean consumer.

Display (0.3.0): a calculator declares how its readings read best (`display` or `displayFor(params)`: `progress`, `volume`, `slo`); a metric definition may override it in `metric_spec.display`, parsed strictly by `StoredMetricSpecSchema` and kept outside the series hash. `slo` needs unit `%` (`displayFits`); an override the unit cannot honour yields to the calculator default. Every goal KPI carries the resolved `metric.display`, its 30 daily `trend`, and `recent` (last 24 hourly buckets) when the metric refreshes hourly or faster. Readers must not infer display from units.

Node calculators (0.4.0): `createGoalMetrics({ nodeCalculators })` registers calculators over sources only that node owns (for example the operator's release tables; ids match `MetricSpecSchema.calculatorId`, so `deploy.release-success@1`, never an underscore) after the package calculators and admits them in the same `node-members` scope. A node calculator may not use a published family (`work.count`, `work.convergence`, `github.stars`) at any version (`reserved_calculator_family`; `RESERVED_CALCULATOR_FAMILIES`), so the package keeps every future version of its own ids; nodes name theirs in their own families (for example `deploy.*`, `node.*`). Two node calculators cannot share an id (`duplicate_calculator`). The service enforces each node calculator's `timeoutMs` and `maxSourceCalls` exactly as for built-ins; sources must honour `maxRows` and `maxResponseBytes`. An id the spec schema rejects throws `invalid_calculator_id`, and a definition naming an unregistered calculator stays `metric_not_found`. The package contract above covers only `PACKAGE_CALCULATOR_IDS`; each node owns and versions its own calculators. A calculator that reads private connection data must not be injected here until it carries its own grant check.

`brief.conformance@1` (params `{subject: items|entries, maxLongShare 0..0.5}`, unit `%`, one source call, 5000 rows, 16 MiB, 15 s) scores open work items or live hub entries with `brief-rules@1`; the value is the share that pass every agent-fixable rule, and rows that break only the human-gated `Goal =` rules stay counted and pass (`human_gated_failing=K` in evidence). Any change to a rule, list, limit or evidence string is a version bump. The terminal `metric.compute.completed` event carries `reason`. Doltgres 0.57.3: `octet_length` panics on stored long text unless wrapped in `substr`, and a bare `SUM` compares as text, so the statement casts it to `BIGINT`.

No package-served definitions (0.8.0): `definitions.get` and `list` read reviewed hub rows (`entryType: metric`) only. `BUILTIN_METRICS` and `BUILTIN_METRIC_REVISION` are removed; a package ships calculators, never a definition. A reader on 0.5 to 0.7 that still needs the two retired `brief-conformance-*` ids must read them from hub rows. `brief.conformance@1` stays registered until its own retirement release.

`no-inline-history@1` (0.8.0) reads every no-inline-history metric: a work item or knowledge atom states the current record, and history holds the story. It detects inline-history marker lines (dated updates, revision tags, pasted reviews, strikethrough, `Progress:`/`Update:` labels); it cannot tell whether a record is true. Params are one of `{measure: "state", subject: work-items|atoms}` (unit `%`, the share of open work items or live atoms with no `no-inline-history-rules@1` marker line in title, summary and outcome or title, use_when and content; the statement is the brief-conformance scope statement, one call, 5000 rows, 16 MiB), `{measure: "scope", subject: "work-items"}` (unit `items`, open work items outside fixtures; guardrail) and `{measure: "edits", output: share|count, days: 1..28}` (three calls: the window's commits, then work items, then atoms; an edit is one (commit, row id) pair on main from `dolt_diff_work_items` or `dolt_diff_knowledge` that changed a work item's summary or outcome or an atom's content in `[end - days, end)` UTC; creation, deletion and fixtures are not edits; the window's commits are the hashes in `dolt_log` whose commit date is in the window (one row past the 5000-row cap; more fails closed, evidence `counts:window_commits=N;cap_hit`; none means no diff is read), and only diff rows whose `to_commit` is one of them (a literal chain of `to_commit = '<hash>' OR ...` tests, which Doltgres 0.57.3 plans as index lookups where an `IN` list fails to plan; Dolt never pushes a date filter down, so the read cost follows the window, not the history, bug.0030) and whose edit column changed are read (ordered by row id then date, one row past the 5000-row cap, LEFT joins to `dolt_log` and `knowledge_contribution_commits`; the row and byte totals are window functions in the same pass as the rows, so over a cap the statement sends its first row alone, carrying the totals, and with no qualifying diff row it sends none, read as no edit in that table with the window read's `as_of`); among those, adjacent diff rows of one row id with identical `to_` values collapse to the older (a merge commit repeating its branch commit's row, `counts:merge_repeats`; a contribution's edit may have a diff row at its merge commit only, so one merged inside the window counts at the merge date); an edit appends history when the count of marker lines across its changed columns grows; `share` is the percent that did not append and is `insufficient_history` under 10 edits and `zero_denominator` with none; `count` is the raw total; more than 2000 edits fails closed). Budget 15 s, 5000 rows, 16 MiB, at most 3 calls; a cap hit, an oversize field (over 100,000 characters) or a malformed result is `incomplete_or_invalid_source`, a failed read `source_failed` (evidence `error:<ClassName>`, never the message), a timeout its own failure. The calculator has no historical windows: state is main now, so a past `evaluationAt` is refused. Evidence carries ids and counts, never row text: `rules:no-inline-history-rules@1`, `counts:evaluated=N;passing=M`, `rule:<code>=<n>`, `rule:oversize=K`, work items add `missing_goal=K;missing_done_when=J` (never part of the value), up to 10 `worst:<id>:<code>`; edits carry `window:[start,end)`, `counts:edits=N;appending=M;withReason=R` (R: work-item commits with a `Reason:` line after the first, atom commits with a contribution message) and `counts:merge_repeats=K`. `no-inline-history-rules@1`: strip list, quote, heading and bold marks; fenced code, checklist lines and link-only lines never match; `dated_line` counts only when one field holds two or more; `Status`, `State`, `Due` and `Owner` are never labels; a marker change is a version bump of the rules and the calculator.

Serves and band (0.9.0): a stored `metric_spec` may carry `serves: {kpi, role: input|diagnostic|guardrail}` and `band` (a KPI binding without `metricId`, `evaluationAt` and `baselineObservationId`; keeps `comparator`, `target`, `breach`), parsed strictly by `StoredMetricSpecSchema` and returned by `parseStoredMetricSpec`. Both sit beside the spec like `display`: they never enter `MetricSpecSchema` or `metricDefinitionHash` (`{id, spec}`), so adding or editing them does not fork the series. A band is assessed as the synthetic binding `{metricId, ...band}` through `service.kpi(b, {latestOnly: true})`, the one assessment path; `latestOnly` skips the trend and recent queries. `MetricView` (and so `GET /api/v1/metrics` and `/{id}`) carries `definition.serves`, `definition.band` and `bandAssessment` (absent without a band). `service.serving()` lists registered metrics that declare `serves` with their band assessment, scanning at most `SERVES_SCAN_MAX` (200) definitions. `GET /api/v1/metrics/goals`: each `GoalKpi` gains optional `served: [{metric: {id, title, calculatorId, role}, assessment}]` (assessment is null when the metric has no band); the read gains `orphans: [{metricId, kpi, reason: "serves_unknown_kpi", assessment}]` for metrics whose `serves.kpi` no goal binds, and `servedTruncated` when the scan was cut. Both are absent when the node has no metrics service, and when the served read fails (for example `metric_authority_unavailable`): the goal read then still succeeds and carries `servedUnavailable: <code>`. A hypothesis prediction's KPI is a valid `serves` target (not `serves_unknown_kpi`), but no goal card lists the metric, so since 0.10.0 it is an orphan with reason `serves_bet_kpi`. `parseStoredMetricSpec` parses the core spec (and `display`) strictly and `serves`/`band` separately: only an invalid core skips the row and logs `metric.definition_invalid`. An invalid `serves` or `band` is ignored, the metric keeps computing and is assessed with its spec, and the definition carries `annexInvalid: [{field, issues}]`; the goal read reports it in `orphans` with reason `serves_invalid` or `band_invalid` and zod issue paths such as `serves.role:invalid_value` (never stored values). An unknown KPI is valid and surfaces as an orphan with reason `serves_unknown_kpi`. A reader older than 0.9.0 rejects a stored spec that carries either field (strict schema): upgrade readers before any hub row sets one.

Breach (0.6.0): a KPI binding may set `breach: "failing"`. Before the deadline, a fresh good reading that misses the comparator is then `failing` with reason `target_breached` instead of `behind`. A stale reading stays `delayed`, a failed attempt keeps its own reason, and after the deadline `met` / `missed` is unchanged. Without the field nothing changes. A reader on a package older than 0.6.0 rejects a binding that carries the field (strict schema), so upgrade readers before any goal row sets it.

HTTP core (0.7.0, `./http`): `createMetricHttpHandlers({ goalProgress, service, subject, onUnexpectedError })` returns `goals()`, `list(query)`, `read(id)`, `history(id, query)`, `observation(id, observationId)`, `compute(id, readJson)` and `subject(id)`, each resolving to `{ ok, status, body }`: success bodies are parsed with the wire schemas (`MetricReadResponseSchema` is the `/{id}` shape); invalid input is 400 `invalid_input` (with `issues` for history and compute), a bad observation id 400 `invalid_observation_id`, unparseable JSON 400 `invalid_json`, a pending compute 409, an absent or non-goal subject 404 `subject_not_found`, a `MetricError` keeps its `code` and `status`, and anything else is 503 `metrics_unavailable` after `onUnexpectedError(error)` (the message never reaches the caller). No Next.js, container, auth or logging-sink imports: a node route keeps authentication, path parameters, request logging and converting the result to its framework's response (send `METRIC_HTTP_HEADERS`, `Cache-Control: no-store`). Error codes and statuses are a published contract: changing one is a version bump. The matching UI is `@cogni-dao/knowledge-base-ui/goals` (>= 0.7.0).

Metrics page read (0.10.0, story.0039): `GET /api/v1/metrics/goals` (and `core__goal_progress`, which returns the same body) carries every registered metric once, grouped by the server. Each `served` and `orphans` row gains `latest` (`{viewState, value, unit, observedAt, reason}`: the newest attempt's state, the last good value and its time, banded or not), and an orphan gains `title`. The read gains `unbound: [{metric: {id, title, calculatorId}, assessment, latest}]`: metrics with no `serves` that no goal binds as a KPI (a goal KPI's own metric is never unbound; a bet-only KPI metric is listed). `service.serving()` now returns `{items, unbound, truncated}` over one scan of at most `SERVES_SCAN_MAX` definitions; each definition page uses one authorized latest/last-good observation batch (`workReadBatch`; the band assessment reuses its rows through `kpi(..., {preloaded})`): no history range read and no second definition read. `core__metric_list` / `GET /api/v1/metrics` return the flat list (`definition.serves`, `band`, `bandAssessment`, `latestAttempt`, `viewState`) for an agent that wants every metric page by page. Each definition is guarded: a metric whose reading cannot be read lists with `latest.viewState: "error"` and never drops the list; observation reads run once per bounded definition page, without per-definition fan-out. All new fields are optional, but the orphan `reason` enum gains `serves_bet_kpi`, so upgrade readers (`@cogni-dao/knowledge-base-ui`, `@cogni-dao/ai-tools`) before the node serves 0.10.0: a 0.9.x schema rejects that value. The Metrics view needs 0.10.0 (`hasMetricDetail`).

Goal-progress read admission (0.12.0, bug.0035): `createGoalProgressReader` runs one shared read per reader, and callers that arrive while it is in flight join it instead of starting another. The shared read has an 8 s deadline of its own (`readMetricBudget`'s optional `timeoutMs`; per-metric batch reads keep 2.5 s) and is not aborted when a caller stops waiting, so a read that needs more than 2.5 s finishes and serves the callers that joined it. A result with no `servedUnavailable` and no `hypothesesUnavailable` goal is kept as the last good one. Exception to the fresh-read rule (performance-expert axiom 6): with a last good result under ten minutes old, a caller waits 2.5 s for the fresh read, then is served the last good result; a fresh read that fails, or completes degraded, is replaced by it too. That body carries `stale: {reason: fresh_read_slow | fresh_read_failed | fresh_read_degraded, ageSeconds}` (seconds since its `asOf`), a fresh body never does, and the route logs `stale`, `staleReason` and `staleAgeSeconds` on `goals.progress_read`. A caller with nothing to serve waits for the read, then gets a retryable 503 `batch_unavailable` (the route adds `Retry-After: 2`). The last good result is per process: a new process still waits up to 8 s for its first read. Before it is served, every definition the read that produced it was authorized to list is re-checked with `MetricService.canRead` (the same `authorize("read")` a fresh read makes); if any is no longer readable, or the check fails or is not answered within 500 ms, nothing stale is served and the caller waits for the fresh read. The check covers the metric list the read scanned; hypothesis predictions carry no metric identity of their own. The cap of four unsettled reads per port is unchanged.

`work.count@1` mode `kpi-linked` (0.11.0, task.0113): the percent of open, non-synthetic work items whose `moves` names at least one metric (unit `%`, display `progress`; `open` and `validated` stay `items`). One call, one statement of two scalar COUNTs over `work_items` (`moves` is NULL when never declared and `[]` when cleared; an entry always carries a `metricId` key, so `CAST(moves AS TEXT) LIKE '%"metricId"%'` counts entries only). An empty scope is `zero_denominator`; a malformed result is `incomplete_or_invalid_source`; a failed read throws. Evidence: `node:work_items:count:kpi-linked:excludes-synthetic`, `counts:evaluated=N;linked=M`. A reader on 0.10 or older rejects the new mode (strict params schema), so adopt 0.11.0 before a reviewed definition uses it.

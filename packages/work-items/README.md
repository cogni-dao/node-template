# Work items 0.2

Dolt owns versioned work-item content. PostgreSQL owns live operational leases; `withWorkItemLeases` composes the two ports. Heartbeat and release return lease-only receipts and never query Dolt. Lease renew/release require the current acquisition token; an old run cannot control its successor. Content writes return the committed content result without a post-commit lease lookup. Hard deletion is retired; cancel an item while preserving its identity and history.

The Dolt content adapter requires an independent reader client or reader factory. Ordinary GET/list/relation reads never reserve a writer session, acquire advisory locks, change branches, or reconcile writes. One read deadline covers FIFO waiting and native execution, without automatic retry. Each reader permits its configured pool width of actual queries plus at most 32 waiting callers; a queued caller cannot dispatch SQL after its deadline or generation retirement. This provisional burst allowance is not a fleet-capacity certification. A timed-out generation stops receiving queries but retains its sockets and slot until every actual native query finishes; no grace timer destroys pending work. At most two reader generations can coexist; another replacement is refused until a generation has actually drained. A retired generation cannot be reused. An injected factory owns its pool options and must budget two pool widths; `readConnectionBudget` validates their combined total and fails closed on unknown widths. This does not increase query deadlines or writer budgets.

The template injects width-one readers with `readConnectionBudget: 2`: at most two reader connections during recovery overlap, plus its dedicated width-one writer. The prior derived reader had width one; the additional transient connection is deliberate fault containment. Each consuming node must review its own existing connection allowance rather than assume the same width. Doltgres 0.57.3 does not implement protocol CancelRequest, and client `end(0)` or process exit does not prove that native work stopped.

A writer caller deadline abandons that intent while its actual query/acquire retains the FIFO ticket, socket and guard, until it settles or until settlement (after a 15 s grace) ends its pool. Retries receive `WorkItemsCapacityError` before issuing SQL or constructing another pool. At most 32 operations may wait for ordinary admission; an abandoned native operation admits no further waiters. A successful late pre-guard prime releases capacity without invoking the abandoned callback, so a new request can reuse the same pool. Positively acknowledged late advisory locks are released before reuse. Post-branch abandonment returns the current nonretryable lookup receipt. After authoritative native settlement, private cleanup may release the guard only after proving clean main or reconciling the positively owned operation branch. Reset is restricted to owned uncommitted changes at the captured base, before any commit or merge attempt; the operation ref and issued receipt remain available. The abandoned callback never resumes. Failed state proof quarantines the lane. Transport rejection is UNKNOWN, not authoritative native completion, but only from the first writer-lock request onward. Before that request (the pool probe, reserve, `current_database()`), the session holds no lock and has changed nothing, so a transport failure is an ordinary retryable 503 that holds nothing (bug.0042).

A held writer settles without a restart (bug.0042). Writes return `WorkItemsCapacityError` while it is held. An unknown outcome starts settlement at once; a pending one starts after a 15 s grace. Settlement retries on exponential backoff with equal jitter, from 1 s up to 30 s. Each attempt:
1. Ends the held generation's pool. Closing is never taken as proof.
2. Builds a fresh writer and takes the writer advisory lock on it. Doltgres frees a session's advisory locks when the session ends, so a free lock proves the old session holds none.
3. Runs the restart reconciliation under that lock, then reopens admission.

Settlement never replays the abandoned callback. A late report from the retired generation is ignored. `writerHealth()` reports the hold without a database call, and nodes surface it in deep readiness. The `adapter.work_items.writer_held`, `writer_refused`, `writer_settle_attempt` and `writer_recovered` events record each transition. A reader generation still stays quarantined and counted after a transport rejection.

These are per-process pool bounds, not a deployment-wide budget. Budget every independent writer, reader generation, replica, replacement and migration producer explicitly. Native work can survive client or process exit and remains part of that overlap until actual completion/cleanup is observed. The restart fixture admits two max-one producer generations and verifies finite cleanup, committed-intent readback and no duplicate/replayed DML; that fixture allowance is not a production limit. Doltgres 0.57.3 has no demonstrated native per-node/global admission enforcement, and these checks do not certify isolation, indefinite-stall recovery or 100-node capacity. Fleet activation still requires the reviewed old-producer cutover and exact-live-build proof.

A settled explicit-ID duplicate currently takes the work-item adapter's session-retirement path. Canonical DI supplies a fresh width-one writer factory; the native acceptance lane checks duplicate rejection, accounts for the two successive native generations, waits for the retired PID to disappear, and admits one distinct fresh create. A constructor without `recreateClient` remains unavailable after that path and cannot settle a held writer. Recreation alone never resolves unknown native transport: the fresh session must win the writer lock first. This behavior does not provide a deployment-wide capacity bound.

Writer `bridge` mode holds both legacy advisory keys and a common native-database key across the complete mutation/recovery scope. It protects same-database work/knowledge callers while legacy clients are drained. Explicit `database` mode removes the process-global legacy keys only after that database has no old callers, including previously unguarded raw knowledge writers. Package installation alone does not prove that cutover or fleet adoption.

A current write whose commit or recovery outcome cannot be proved raises `WorkItemWriteOutcomeUnknownError` with `retryable: false` and a lookup receipt containing its operation ID, branch, optional commit hash and item ID. HTTP create/patch return 409 with that receipt; callers must inspect it before replaying. A failure while reconciling an older orphan before the current intent runs remains a busy admission failure. A canonical, positively proven lost acknowledgement still returns the committed result.

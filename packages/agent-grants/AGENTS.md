# agent-grants

Published `@cogni-dao/agent-grants` owns runtime tool authority: `authorize()`, role-row reads and writes, and `guardTools()` that wraps every tool runtime's `exec`.

- A tool runs only when its graph lock, principal lock and subject lock open. Read-only tools need only the graph lock. Design: https://cognidao.org/knowledge/node-capability-grants-standard (section "Runtime identity does not depend on hosting").
- No private `@cogni/*` import, no app ExecutionScope, no ai-core import. Runtimes are structural (`id`, `effect`, `exec`). The node passes `withStore`, `adminCheck`, `onDecision` and `runAs`.
- `/postgres` adapter (exported from the root) takes an injected tagged-template function. It never creates a client or switches a role. `agent_roles` has FORCE RLS and no policy, so only a service-role connection reads or writes it. `agent_principals` has a read-only select policy for every role (the wallet-binding trigger needs it); only a service-role connection writes it.
- A denial throws `ToolAuthorityError` with `receipt {code, retryable:false, lookup}`. The message is fixed and never names a role or scope.
- Every authenticated caller is the run subject, bearer agents included. A subject only narrows: `admin` means a principal the DAO approved; no AI identity is approved yet (item I2), so an agent fails `admin` tools, passes `member` tools, and `own` tools run on its own rows.
- ONE_GRANT_ROW (task.5465, 0.6.0): node and account grants are one `agent_roles` row; `resource` (`node` | `account`) and `account_id` say which, and the declared scope kind picks it (`account` kind: account row, profile page, the account owner approves; any other kind: node row, `/admin/ai-access`, a node-admin approves). RESOURCE_SPLIT: every node-plane store method acts on `resource = 'node'` rows, every account method on `'account'` rows, so a node row never opens an account tool and the reverse. An account row is DURABLE: no end date, it lasts until Off like a node row (task.5465). It is live when approved, unrevoked and (`expires_at` is null or in the future); a row that carries an end keeps the expired state read from `expires_at` (R14), and an expired row is closed (`revoked_at = now()`) before the next ask or direct On of the same (AI, scope). EXPAND PHASE: the old live index (principal, scope) stays, so one open row exists per (AI, scope) and an AI holds one account per account scope until the contract migration (task.5484).
- Account authority: an `account` tool is decided only against an account. `authorize()` and `offeredToolIds()` take `RunIdentity.accountId` (the run's account) and need `hasLiveAccountGrant(principal, scope, accountId)`; with no account they deny `no_account` (R13; the same call at run start and at exec). `authorizeAccount(store, {callerUserId, via, scope, accountId})` is the one answer for account data on a route: `owner` | `delegated` (a bearer agent with a live row for exactly this account) | `null` (the route says one non-disclosing 404; an outage throws and is 503). `authorizeCaller()` calls it for an account scope.
- One link, one gate (`approval.ts`): `requestAccess` writes the Off row and a one-time link token (32 CSPRNG bytes, stored only as sha256, 24 hours, a re-ask rotates it); it returns `approvalPath(kind, token)` and the node adds its origin. `canApprove(store, me, row)` is the ONE gate for approve, deny and revoke: never the asking principal; a node row needs `me.admin` (the admin session); an account row needs `me` to own the row's account (or, for an ask with no account yet, to own an account at all). `approveAccountAsk`, `denyAccountAsk` (by token: an undecided ask has no account, R15), `grantInternalOnAccount` (direct On for this node's AI only, no ask) and `revokeAccountRow` (by id, owner join in the SQL) all pass it, and the decide SQL carries the owner join itself. `previewAsk` finds a waiting ask by token and page resource; a wrong-kind, used, expired or unknown token is one null.
- `node-ai.ts`: `buildNodeAiView` (admin, node rows) and `buildAccountAiView` (profile, the viewer's own account rows plus a pending ask opened by link); `buildAskView` is the one pending row. PROFILE_NEVER_SHOWS_NODE_ROWS, ADMIN_NEVER_SHOWS_ACCOUNT_ROWS.
- CONFORMANCE (SUITE_GATES_RELEASE): `@cogni-dao/agent-grants/grants-conformance` exports `runGrantConformance(harness)`: owner, live grant, expired, revoked grant, wrong scope, foreign account, missing grant, the one gate, the one-time link, direct On for this node's AI only. The package runs it over a memory store (`tests/grant-conformance.test.ts`); every adopting node MUST run the identical rows over its real SQL store (node-template: `app/tests/component/db/agent-account-grants.suite.ts`, with row-level security checked as the real app role). The "revoked key" row lives in the credential suite.
- `node-ai.ts` builds the table rows (Who · Can do · Until · On), one per grant row, in three blocks (asks waiting, this node's AI, outside agents). Name and description come only from the declarations (`requires.label`, `requires.description`); NAMES_ARE_IDENTIFIERS: Who is this node's AI by its slug and an outside agent by its registered name (never a vanity label). There is no copy table and no display name.
- `roles.ts` holds the ask (`requestAccess`: a pending row, `approved_by` null, for the caller only, plus its one link) and the admin's yes (`grantRole`: approves a pending ask, or grants an internal AI directly), no (`denyRequest`) and take-back (`revokeRole`), each taking `me` (`ApprovalCaller`) for the one gate. LIVE_NEEDS_APPROVAL: `hasLiveRole` and `liveScopes` count only rows with an approver and no revoke, so a pending ask opens no lock.
- `same-door.ts` is SAME_DOOR: `SAME_DOOR_ROUTES` maps each write tool to the route ids that twin it (the artifacts route `work.items.artifacts.create` is the twin of `core__work_item_artifact_record`, under the same `work_item:transition` scope; no new scope), `ROUTE_ONLY_CAPABILITIES` declares routes no tool twins (`knowledge.contribute`), `NO_ROUTE_TWIN` allowlists tools with no node route, and `authorizeCaller()` is the route door (a bearer is its own principal and needs a live role row; a human session passes the subject rules). A parity test in `@cogni-dao/langgraph-graphs` fails on any unmapped write tool.
- DENY_BY_DEFAULT (bug.0045, 0.7.0): a bearer write needs a declared door. `same-door.ts` names the doors (`SAME_DOOR_ROUTES`, `ROUTE_ONLY_CAPABILITIES`) and `OPEN_BY_DESIGN_ROUTES`, and exports the pure decision `bearerWriteRefusal({ method, via, doorRuns, bearerWrite, routeId })` (with `SAFE_METHODS`): it returns `{ code: "bearer_write_undeclared" }` for a bearer write (any method but GET, HEAD, OPTIONS; `via` anything but `session`) with no running door, no `bearerWrite` reason (a route that touches only the caller's own data) and no open-by-design entry, else `null`. The node's route wrapper calls it before the handler and answers 403; it owns only the response and the log. `DEFERRED_WRITE_ROUTES` lists writes that stay refused for bearers. Release note (0.7.0, behaviour-visible: `work_item:transition` covers create, claim, release and heartbeat, `knowledge:contribute` covers domain register, four deferred keys removed): a fork gets deny-by-default ONLY by calling `bearerWriteRefusal` from its own route wrapper; once it does, its own undeclared bearer write routes answer 403 until each declares a door, a `bearerWrite` reason or an open-by-design entry.
- ONE_ADMIN_CHECK (task.0140, 0.7.0): an `admin`-subject scope always runs the injected admin check. The subject decides when a run serves one; with no subject (a scheduled run, a bearer route), the principal's own bound wallet decides. A role row alone never passes an `admin` scope, and a bearer is no longer downgraded to `member`. Release note: an internal AI run that used an admin-subject scope with no human subject is now denied until its principal holds an admin wallet.
- ONE_PRINCIPAL_WRITER / KIND_IS_THE_ROW (task.0144, `principals.ts`): `writeExternalPrincipal(tx, userId)` is the one idempotent writer of an outside agent's `agent_principals` row; a node's registration calls it with its user insert in one transaction, and the 0044 migration backfills earlier agents. The key upgrade writes no row: it REFUSES a user with no principal row (a human, reason `wallet_user`, 403 `not_agent_key`), so an agent with a bound wallet upgrades and a human never does. `principalKindOf(sql, userId)` answers `org` (a row of kind org), `agent` (any other row) or `human` (no row), the only read of kind.
- DENIAL_IS_TERMINAL: `offeredToolIds()` drops tools whose principal lock already fails, and `guardTools` calls `onTerminalDenial` once per exec-time denial so the node ends the run cleanly.
- Roles are never cached. A revoked role denies the next call.
- Declared scopes live in the node, derived from the `requires` on its tool contracts. `grantRole` rejects an undeclared scope.
- Build declarations only with tsc; tsup owns JavaScript.
- `@cogni-dao/agent-grants/credentials` (subpath; a node adopts it alone) owns revocable hashed agent keys (key = `REVOCABLE_KEY_PREFIX` + 43 base64url chars of 32 random bytes + a 6-char base62 CRC32 checksum; `key-format.ts` is the one definition: `formatRevocableKey`, `isWellFormedRevocableKey`, `REVOCABLE_KEY_SCAN_PATTERN` for secret scanners; TOKEN_HASH_ONLY, the store sees sha256 of the whole token): `verifyBearer`, `upgradeSignedKey`, `rotateCredential`, `confirmCredential`, `revokeCredential` over a `CredentialStore` port plus the Postgres adapter (`createPostgresCredentialStore(client, { hasRoles })`, a service-role `begin`-capable client; `hasRoles` is the node's read of "does this principal hold roles": node-template passes `agentRolesHasRoles(client)`, the operator passes its OpenFGA read. Every store call first verifies once per instance that the role bypasses RLS (`rolbypassrls` or superuser) and otherwise throws, so a wrong role is 503, never a silent "never confirmed"). State (pending, active, renew_only, expired, revoked) is derived from timestamps by the SQL function `agent_credential_state`, read against the DATABASE clock; it is never stored. A store outage is `unavailable` (503), never `invalid` (401). Rotate supersedes a repeat call; confirm is idempotent and retires the predecessor in one transaction. `migrations/agent_credentials.sql` + README is the migration template (a node generates its own snapshot). The v1 HMAC verify stays in the node and is not touched; after it, the node calls `assertV1NotSuperseded` so a user with a CONFIRMED revocable key (revoked or not) can no longer use signed keys (`V1SupersededError`, 401 `v1_superseded`). Any store failure at any step surfaces as `CredentialStoreUnavailableError` (503). A token with the wrong shape or a failing checksum is refused before any store read; `verifyBearer(store, token, allow, { admit })` calls the node's per-IP `admit` after the shape check and before the store (over the limit = `rate_limited`, the node answers 429). BINDING_BEFORE_UPGRADE (roles and no GitHub binding = `binding_required`) runs at upgrade AND again at confirm for an upgrade key. CONFORMANCE (SUITE_GATES_RELEASE): `@cogni-dao/agent-grants/conformance` exports `runCredentialConformance(harness)`; the harness passes the test runner, creates users, moves timestamps and breaks the store. The package runs it over a memory store (`tests/credentials.test.ts`); every adopting node MUST run the identical rows over its real SQL store (node-template: `app/tests/component/db/agent-credentials.int.test.ts`).
- ORGS (story.0038, 0.8.0, subpath `./orgs`; migration template `migrations/agent_principals_orgs.sql`): an org is an `agent_principals` row of kind `org` with `owner_source_kind` and `owner_source_ref` (unique partial index: one org per source). `OrgSource` is `{ kind: "repo-spec", ref, path? }` or (0.9.0) `{ kind: "issuer", ref }` where `ref` is a signing issuer's canonical https origin (a customer node's record on a provider: `ensureOrg` keys it by the origin, a candidate and a production origin are two orgs; `createIssuerOwnerSource()` throws `OwnerSourceUnavailableError("issuer_has_no_owners")` for it, and `createOwnerSources([...])` dispatches by kind; no schema change: `owner_source_kind` is plain text). For a repo-spec source: `path` (default `.cogni/repo-spec.yaml`; a monorepo node uses `nodes/<node>/.cogni/repo-spec.yaml`) must be relative, forward-slash, free of `.`/`..`/empty segments and end in `.cogni/repo-spec.yaml`, else `InvalidOrgSourceError`. The stored `owner_source_ref` is the canonical key `https://github.com/<o>/<r>` plus `#<path>` only when the path is not the default (so existing refs are unchanged); two paths in one repo are two orgs, the owner-source cache key is that canonical key, and `fetchRepoSpec(ref, path)` receives the plain repo URL and the path, on its own `users` row that owns ONE ordinary `billing_accounts` row (and its default virtual key). `billing_accounts` is never polymorphic; there is no orgs table, no owner snapshot and no `account:spend` scope. `ensureOrg(tx, source)` is idempotent and keyed by the source (`tx` is a service-role transaction; it serializes with a transaction advisory lock). OWNERS_READ_AT_DECISION: `OwnerSource.owners(OrgSource)` returns principal user ids; `createRepoSpecOwnerSource({ fetchRepoSpec, extractApprovers, usersForWallets, ttlMs, now })` maps `activity_ledger.approvers` only (never the steward wallet), lowercased, to users, and holds the ONE cache of that FINAL list per ref (`ttlMs` 0 to 300000, default 300000; 0 = no cache and no single-flight; concurrent misses share one read; a value is never served past its ttl). Any failed read, and a repo-spec that lists no approvers (`reason: "no_approvers"`), throws `OwnerSourceUnavailableError` and is not cached. `createOwnerSources([...])` dispatches by kind. `fetchRepoSpec` is an injected dependency of the owner source; `createGithubRepoSpecFetcher({ fetch?, token?: () => Promise<string | undefined> })` (over `fetchRepoSpecFromGithub(ref, path, opts)`) is the ready-made default: the GitHub contents API (`Accept: application/vnd.github.raw`, never the raw CDN), github.com only, 10 s, 64 KiB, redirect is an error, an optional token PROVIDER function (the package reads no env var) sent as a bearer, a 403/429 or any failure is `OwnerSourceUnavailableError`. `canApprove(store, me, row, owners?)`, `authorizeAccount(store, { ..., owners })` and `authorizeCaller(..., { owners })` ask the owner source only when the account's owner user is an org (`store.orgSourceOfAccount`, optional on the port); `authorizeAccount` reads the owner user, then the bearer's live grant row, then the org's owners, so a live grant never waits on the owner read (a GitHub outage stops no delegated call); a human-owned account is byte-for-byte unchanged and NO_SELF_APPROVAL still holds. The approve/deny/revoke SQL still joins `billing_accounts.owner_user_id = approver`, so deciding on an org account through those statements lands with the payer binding (phase 2). `principalKindOf` answers `org`.
- SERVICE_AUTH (story.0038, 0.8.0, subpath `./service-auth`): a service on a home node calls a target with a short-lived RFC 7523 assertion (Ed25519 over Web Crypto, no dependency). `createServiceAssertionSigner({ issuer, kid, privateJwk, now })` signs `{ service, audienceNodeId, scope }` (claims iss, sub, aud `urn:cogni:node:<id>`, client_id `<iss>#<sub>`, scope, iat, exp <= iat + 300 (the signer uses 120), jti; header EdDSA, kid, JWT) and serves `jwks()` (public members only). `createServiceAssertionVerifier({ selfNodeId, trustedHomes, fetchJwks, replay, now })` returns `{ ok: true, issuer, service, clientId, scope, jti }` or `{ ok: false, code }` (`untrusted_issuer`, `bad_signature`, `wrong_audience`, `expired`, `replayed`, `service_not_allowed`, `malformed`, `jwks_unavailable`; a refusal may carry the UNVERIFIED `issuer` and `service` for the log only). JWKS is cached by kid; an unknown kid refetches at most once a minute and then fails closed; a cached key older than an hour is refetched. `exp - iat > 300` is `malformed`. `ReplayStore.seen(jti, expiresAt)`; `createMemoryReplayStore()` is bounded and SINGLE REPLICA ONLY (several replicas need a shared store). `ensureServicePrincipal(tx, { issuer, service })` writes one external principal on its own users row (id derived from sha-256 of issuer and service, so it is idempotent and has no credential rows); `findServicePrincipal` reads it; `requestServiceAccess({ tx, store, assertion, scope, ... })` writes ONE pending ask (the ordinary ask row). `parseTrustedHomes(json)` parses the trusted-homes config (https issuer and `jwksUri`, only services matching the exported `SERVICE_SLUG`; unusable input is `[]`), and `assertSigningKeyMatches(privateJwk)` proves a private JWK's `x` belongs to its `d`. A verified assertion grants nothing: the grant row decides every call.
- SERVICE_AUTH_CONFIG (story.0038 phase 2, subpath `./service-auth`): `createServiceAssertionSignerFromSeed({ issuer, seedHex, now? })` derives the Ed25519 key pair from a 32-byte seed (64 hex characters; the operator generates and stores it, so no human pastes a key): PKCS#8 prefix `302e020100300506032b657004220420` + seed, imported through Web Crypto, and `kid` is the RFC 7638 JWK thumbprint of the public key (`ed25519Thumbprint(x)`). A malformed seed throws a `TypeError` that never carries the value. The JWK variant `createServiceAssertionSigner({ issuer, kid, privateJwk })` stays for an operator that keeps its own key. Public URLs are Git config, not env: `parseTrustedHomes(raw)` (`[{ issuer, jwks_uri, services }]`, returns `TrustedHome[]`) and `parseLinkTargets(raw)` (`[{ alias, node_id, origin }]`, returns `LinkTarget[]`, with `LINK_ALIAS`) take the already-parsed lists of a node's `.cogni/service-links.yaml` (the section named by `DEPLOY_ENVIRONMENT`, read by `parseServiceLinksFile` in `@cogni/repo-spec`). Both are strict per entry (canonical https origins, slug-shaped aliases and services, `jwks_uri` over https; any other entry is dropped, a repeated alias keeps its first) and fail closed: not a list means none. 0.9.0 additions to `./service-auth`: `ServiceAssertionRequest.claims` (extra signed claims: primitives under lowercase names that are not registered claims, at most 8, strings at most 200 characters, `iss sub aud client_id scope iat exp jti nbf typ` are reserved and throw `TypeError`) and `VerifiedServiceAssertion.claims` (the verified extras, empty for an ordinary call); `createPostgresReplayStore(sql)` (the DURABLE replay store over `service_assertion_jtis`: `jti` primary key, an expired row is taken over, at most 200 expired rows are pruned per call, the expiry is an ISO string; a failure rejects, never passes; the node swaps it for the in-memory store and a restart or a second replica can no longer replay); `NODE_CONNECT_SERVICE`; an optional `node_id` on a `trusted_homes` entry (`TrustedHome.nodeId`, a label for the provider's page, never a trust input) and an optional `offer` string on a `targets` entry (`LinkTarget.offer`, static text of at most `MAX_OFFER_CHARS` for the customer's page); `isCanonicalHttpsOrigin` moved to a shared module and is still exported here.
- PAYER_BINDINGS (story.0038, `payer.ts`; migration template `migrations/payer_bindings.sql`, unchanged in 0.9.0): the run path's payer rows. A run bills an account other than the caller's own only through a live `payer_bindings` row (PAYER_IS_AUTHORIZED; no `account:spend` scope). Since 0.9.0 the ONLY writer of a live row is a signed connect (`connections.ts`: one row per service principal of the connecting issuer, approved by the issuer's own org user); the 0.8.0 request, decide and revoke functions (`requestPayerBinding`, `decidePayerBinding`, `revokePayerBinding`, `ownersForBinding`) and their store methods are gone (no person approves a binding; the customer node's signed connect does, and the provider's admin suspends it). What stays is the read side: `payerFor(payer, subjectUserId)` (a live row's account or null; read on every call, never cached) and the two pure run-path decisions `selectRunPayer({ payerFor, getAccount }, { subjectUserId, own })` (`{ account, bound }`: the bound account only for a live row naming another existing account, else `own`; a failed read throws) and `payerScopeUserFor(deps, { actorUserId, billingAccountId })` (the account owner's row-level-security scope, only when the actor's live row names exactly that account), over the `PayerBindingStore` port (`payerFor` only) and `createPostgresPayerBindingStore(sql)`. The table is service-role only (ENABLE + FORCE RLS, no policy).
- CONNECTIONS (story.0038, 0.9.0, `connections.ts`; migration template `migrations/org_connections.sql`): connect from home. A customer node's admin connects from its own Admin page; its node signs ONE assertion as service `node-connect` (`NODE_CONNECT_SERVICE`, scope `CONNECT_SCOPE` = `connection:write`) whose extra signed claims are `act` (`connect` | `disconnect`), `cap` (integer credits) and `seq` (a rising integer, at least 1); the provider verifies it with the one verifier (trusted home, JWKS, audience, expiry, durable `jti`) and keeps ONE thin customer record per signing issuer: an `org` principal of source kind `issuer` (`ensureOrg(tx, { kind: "issuer", ref: <issuer origin> })`, one ordinary billing account, no owners) plus ONE live row in `org_connections` (status `connected` | `disconnected`, `suspended`, `cap`, `seq`). Sibling table, not extra columns on `payer_bindings`: a payer row is one per SUBJECT (every service principal of the issuer has one, all pointing at the record's account), the connection row is one per CUSTOMER, so seq, cap and the sticky flag have one home. `applyConnection(store, { assertion, services })` takes a VERIFIED assertion and answers `{ ok, record, act }` or `{ ok: false, code }` (`wrong_service`, `wrong_scope`, `invalid_claims`, `stale_seq` with the stored `seq`); `parseConnectClaims`, `ConnectionStore` (`apply`, `get`, `standingOf`, `list`, `setSuspended`, `bindService`) and `createPostgresConnectionStore(sql)` (`apply` and `bindService` need a transaction tag). CONNECT_IS_ORDERED: the seq check and the write are one statement (`... ON CONFLICT (org_user_id) DO UPDATE ... WHERE seq < EXCLUDED.seq`); a seq at or below the stored one is `stale_seq` and writes nothing (cap included), so a replayed body, with a stale jti or a fresh one, changes nothing. A disconnect is a tombstone that keeps the stored cap; a later connect replaces the cap and keeps the cumulative count. SUSPEND_IS_STICKY: `suspended` is its own column written only by `setSuspended` (the provider admin); a connect or disconnect never touches it. ONE_RECORD_PER_ISSUER: a connect binds every service of the provider's own trusted-home entry that ALREADY HAS a principal (except `node-connect`, which is never a principal: `ensureServicePrincipal` refuses it) to the record through live `payer_bindings` rows, and NEVER creates a principal: a connected customer's AI still gets 401, asks, and waits on `/admin/ai-access`; `bindService` (called in the ask's own transaction) binds a service that asks later. SEQ_STEP_IS_BOUNDED: a `seq` more than `MAX_SEQ_STEP` (1,000,000) above the stored one, or above it on a first connect, is `seq_jump` (409 on the route, with the stored seq, nothing written, not even the org) so a stolen key cannot burn the integer line; `ConnectionStore.resetSeq(orgUserId)` is the provider admin's way back (the stored seq to 1, nothing else changes). The gate's read (`standingOf`) sums the account's `charge_receipts` through the covering index `charge_receipts_account_charged_idx` (an index-only scan; template `migrations/charge_receipts_account_charged_idx.sql`) and leaves `lastCallAt` null; `list` (the page) also reads the last receipt time. The run gate: `decideConnection({ status, suspended, cap, balance, debits })` is pure (suspended, then disconnected, then an empty allowance, then the cap: `connection_suspended`, `connection_disconnected`, `connection_allowance_empty`, `connection_cap_reached`); `connectionRefusalFor(store, billingAccountId)` and `assertConnectionAdmits(store, billingAccountId)` (throws `ConnectionRefusedError`, `isConnectionRefusedError` matches by name) read the live standing on every call: the allowance is the credit balance of the record's billing account (a provider admin's own ledger grant), the cumulative debits are the sum of its `charge_receipts`, a run is admitted only while `balance > 0` AND `debits < cap`; an account that is not a connection record is never refused. `viewOf(standing)` is the page row (one display status, suspended wins; `ConnectedOrgView` adds the optional `nodeId`). No route, no logging, no billing write: the node verifies, applies, writes the allowance through its own accounts adapter (reason `connection_allowance`) and answers the gate.
- CONNECT_SENDER (story.0038, 0.9.0, `connect-sender.ts`; migration template `migrations/outbound_connections.sql`): the CUSTOMER side, shared so every node gets it by a version bump. `createConnectSender({ targets, signer, store, fetchImpl?, onSent? })` (`targets` are the `parseLinkTargets` of the node's `.cogni/service-links.yaml`, `signer` is read lazily and may be null, `store` is an `OutboundConnectionStore`) answers `list()` (`{ signer, targets: OutboundTargetView[] }`: alias, origin, static `offer`, status `connected` | `not_connected`, cap) and `act({ alias, act, cap? })` (`OutboundActResult`: the provider's `httpStatus`, `status`, plain `error` code and the target's new view; or `unknown_alias`, `no_signer`, `unreachable`). It takes the next seq atomically BEFORE signing (`reserveSeq`: a restart, a replica or a failed send never reuses one), signs `act`, `cap`, `seq` as `node-connect` for the target's audience, posts once to `CONNECT_PATH` (the configured origin only, https, no redirects, 10 s, 64 KiB), records status and cap only from a provider 200 and only while no newer send has reserved a higher seq (`accept` is guarded by the reserved seq), and lifts its seq above the provider's stored one on a `stale_seq` or `seq_jump` answer (`liftSeq`, a `GREATEST`). `createPostgresOutboundConnectionStore(sql)` is the Postgres adapter (one statement per method, a service-role tag). `onSent` carries alias, act, outcome and status, never a token.
- ORG_DECISION_SQL (story.0038 phase 2): `approveAccountAsk`, `denyAccountAsk` and `revokeAccountRow` take `owners` (and, for an ask, the org's `accountId`). An org's owners are read at decision time and cannot be a SQL join, so `canApprove` with `owners` is the gate and the optional store methods `approveAccountByLinkOnOrg`, `denyAccountByLinkOnOrg`, `revokeAccountRoleOnOrg` and `accountRoleOf` only pin the write to an account whose owner user is an `org` principal. The human-owned statements are unchanged; a store without these methods refuses an org decision. An `issuer` org has no owners (`issuer_has_no_owners`), so none of these statements passes for one.

Also in 0.8.0 (story.0038 phase 2): `migrations/payer_bindings.sql` (a fork mirrors it before using the payer functions); `approveAccountAsk`, `denyAccountAsk`, `revokeAccountRow`, `turnMineOn` and `turnMineOff` take optional `owners` (and an ask's `accountId`) and a store without the optional `...OnOrg` methods refuses an org decision; `parseTrustedHomes` now takes the parsed `jwks_uri` list (not a JSON string with `jwksUri`), a signing key is a `SERVICE_ASSERTION_SIGNING_SEED` through `createServiceAssertionSignerFromSeed`, and the node's trusted homes and link targets come from `.cogni/service-links.yaml`, not env.

REMOVED: `requestPayerBinding`, `decidePayerBinding`, `revokePayerBinding`, `ownersForBinding`, the `PayerBindingStore` methods `openFor`, `get`, `request`, `approve` and `close`, the types `PayerAskOutcome`, `PayerAskResult`, `PayerBindingRow`, `PayerBindingState` and the constants `MAX_PENDING_PER_ACCOUNT` and `PENDING_BINDING_TTL_DAYS` (the operator uses none; the node routes `POST /api/v1/orgs` and `/api/v1/payer-bindings` go with them). KEPT: `OwnerSource`, `createRepoSpecOwnerSource`, `createGithubRepoSpecFetcher`, `canApprove`, `authorizeAccount`, `ensureOrg`, `payerFor`, `selectRunPayer`, `payerScopeUserFor`, `createPostgresPayerBindingStore` (now `payerFor` only) and every `./service-auth` export. ADDED: `./connections` (re-exported from the root: `applyConnection`, `parseConnectClaims`, `decideConnection`, `connectionRefusalFor`, `assertConnectionAdmits`, `ConnectionRefusedError`, `isConnectionRefusedError`, `viewOf`, `createPostgresConnectionStore`, `ConnectionStore` (with `resetSeq`) and the view types, `CONNECT_SCOPE`, `MAX_SEQ_STEP`); `./connect-sender` (re-exported from the root: `createConnectSender`, `createPostgresOutboundConnectionStore`, `OutboundConnectionStore`, `OutboundTargetView`, `OutboundActResult`, `CONNECT_PATH`); the `issuer` `OrgSource` kind and `createIssuerOwnerSource`; `./service-auth`: signed extra `claims` on the signer and verifier, `createPostgresReplayStore`, `NODE_CONNECT_SERVICE`, `TrustedHome.nodeId`, `LinkTarget.offer`, `MAX_OFFER_CHARS`; `ensureServicePrincipal` refuses `node-connect`; `VerifiedServiceAssertion` gains a required `claims` field (a fork that builds one by hand adds `claims: {}`). MIGRATION: new additive templates, none editing 0.8.0's: `migrations/org_connections.sql` (tables `org_connections` and `service_assertion_jtis`, FORCE RLS), `migrations/outbound_connections.sql` (a customer node's own `outbound_connections`, FORCE RLS) and `migrations/charge_receipts_account_charged_idx.sql` (one index the gate's sum reads); a fork mirrors them exactly. 0.8.0's `agent_principals_orgs.sql` and `payer_bindings.sql` are NOT edited: the `issuer` kind needs no schema change and the connect writes ordinary rows into `payer_bindings`. A fork that adopts the connect route must also swap its in-memory replay store for `createPostgresReplayStore` so the connect's `jti` is durable.

# agent-grants

Published `@cogni-dao/agent-grants` owns runtime tool authority: `authorize()`, role-row reads and writes, and `guardTools()` that wraps every tool runtime's `exec`.

- A tool runs only when its graph lock, principal lock and subject lock open. Read-only tools need only the graph lock. Design: https://cognidao.org/knowledge/node-capability-grants-standard (section "Runtime identity does not depend on hosting").
- No private `@cogni/*` import, no app ExecutionScope, no ai-core import. Runtimes are structural (`id`, `effect`, `exec`). The node passes `withStore`, `adminCheck`, `onDecision` and `runAs`.
- `/postgres` adapter (exported from the root) takes an injected tagged-template function. It never creates a client or switches a role. `agent_roles` has FORCE RLS and no policy, so only a service-role connection reads or writes it. `agent_principals` has a read-only select policy for every role (the wallet-binding trigger needs it); only a service-role connection writes it.
- A denial throws `ToolAuthorityError` with `receipt {code, retryable:false, lookup}`. The message is fixed and never names a role or scope.
- Every authenticated caller is the run subject, bearer agents included. A subject only narrows: `admin` means a principal the DAO approved; no AI identity is approved yet (item I2), so an agent fails `admin` tools, passes `member` tools, and `own` tools run on its own rows. Account scopes are out of scope: an `account` tool is denied with `policy_denied`.
- `node-ai.ts` builds the admin table rows (Who · Can do · Until · On), one per grant row, in three blocks (asks waiting, this node's AI, outside agents). Name and description come only from the declarations (`requires.label`, `requires.description`); NAMES_ARE_IDENTIFIERS: Who is this node's AI by its slug and an outside agent by its registered name (never a vanity label). There is no copy table and no display name.
- `roles.ts` holds the ask (`requestAccess`: a pending row, `approved_by` null, for the caller only) and the admin's yes (`grantRole`: approves a pending ask, or grants an internal AI directly), no (`denyRequest`) and take-back (`revokeRole`). An admin can restore the latest previously approved, revoked permission without another enrollment; a newer denied ask never resurrects an older approval. `listRoleRows(limit, declaredScopes, after?)` pages current controls by `(principalUserId, scope)` with `nextCursor`, limit1–100; service Off controls use indexed latest-consent lookups. Hosts/UI must carry the cursor together. SQL role writers take the shared per-user advisory and principal lock in a real transaction before mutating authority. LIVE_NEEDS_APPROVAL: `hasLiveRole` and `liveScopes` count only rows with an approver and no revoke, so a pending ask opens no lock.
- `same-door.ts` is SAME_DOOR: `SAME_DOOR_ROUTES` maps each write tool to the route ids that twin it, `ROUTE_ONLY_CAPABILITIES` declares routes no tool twins (`knowledge.contribute`), `NO_ROUTE_TWIN` allowlists tools with no node route, and `authorizeCaller()` is the route door (a bearer is its own principal and needs a live role row; a human session passes the subject rules). A parity test in `@cogni-dao/langgraph-graphs` fails on any unmapped write tool.
- DENIAL_IS_TERMINAL: `offeredToolIds()` drops tools whose principal lock already fails, and `guardTools` calls `onTerminalDenial` once per exec-time denial so the node ends the run cleanly.
- Roles are never cached. A revoked role denies the next call.
- Declared scopes live in the node, derived from the `requires` on its tool contracts. `grantRole` rejects an undeclared scope.
- Build declarations only with tsc; tsup owns JavaScript.
- `@cogni-dao/agent-grants/credentials` (subpath; a node adopts it alone) owns revocable hashed agent keys (key = `REVOCABLE_KEY_PREFIX` + 43 base64url chars of 32 random bytes + a 6-char base62 CRC32 checksum; `key-format.ts` is the one definition: `formatRevocableKey`, `isWellFormedRevocableKey`, `REVOCABLE_KEY_SCAN_PATTERN` for secret scanners; TOKEN_HASH_ONLY, the store sees sha256 of the whole token): `verifyBearer`, `upgradeSignedKey`, `rotateCredential`, `confirmCredential`, `revokeCredential` over a `CredentialStore` port plus the Postgres adapter (`createPostgresCredentialStore(client, { hasRoles })`, a service-role `begin`-capable client; `hasRoles` is the node's read of "does this principal hold roles": node-template passes `agentRolesHasRoles(client)`, the operator passes its OpenFGA read. Every store call first verifies once per instance that the role bypasses RLS (`rolbypassrls` or superuser) and otherwise throws, so a wrong role is 503, never a silent "never confirmed"). State (pending, active, renew_only, expired, revoked) is derived from timestamps by the SQL function `agent_credential_state`, read against the DATABASE clock; it is never stored. A store outage is `unavailable` (503), never `invalid` (401). Rotate supersedes a repeat call; confirm is idempotent and retires the predecessor in one transaction. `migrations/agent_credentials.sql` + README is the migration template (a node generates its own snapshot). The v1 HMAC verify stays in the node and is not touched; after it, the node calls `assertV1NotSuperseded` so a user with a CONFIRMED revocable key (revoked or not) can no longer use signed keys (`V1SupersededError`, 401 `v1_superseded`). Any store failure at any step surfaces as `CredentialStoreUnavailableError` (503). A token with the wrong shape or a failing checksum is refused before any store read; `verifyBearer(store, token, allow, { admit })` calls the node's per-IP `admit` after the shape check and before the store (over the limit = `rate_limited`, the node answers 429). BINDING_BEFORE_UPGRADE (roles and no GitHub binding = `binding_required`) runs at upgrade AND again at confirm for an upgrade key. CONFORMANCE (SUITE_GATES_RELEASE): `@cogni-dao/agent-grants/conformance` exports `runCredentialConformance(harness)`; the harness passes the test runner, creates users, moves timestamps and breaks the store. The package runs it over a memory store (`tests/credentials.test.ts`); every adopting node MUST run the identical rows over its real SQL store (node-template: `app/tests/component/db/agent-credentials.int.test.ts`).
- `@cogni-dao/agent-grants/enrollment` (subpath, 0.4.0; a node adopts it next to `./credentials`) owns SERVICE ENROLLMENT: a service of another node (operator git-review) earns an X-issued revocable key on this node by one signed request and one admin click (design: https://node-template.cognidao.org/knowledge/node-service-enrollment). `claims.ts` is the wire contract (header `typ: cogni-service-enrollment+jwt`, claim `kind: service.enrollment.v1`, `aud: urn:cogni:node:<uuid>`, `jti`, `exp - iat` at most 10 minutes, one scope, an X25519 PUBLIC `cnf.jwk`; `serviceKeyOf` = `<issuer origin>#<service>`, ONE principal per pair). `verify.ts` (`createEnrollmentTokenVerifier`) checks the token against a list of `TrustedHome`s (EdDSA only, exact audience, typ and kind, the home's service and scope limits; a JWKS outage is `jwks_unavailable`, never an accept); the node injects a cached remote key set per issuer. `service.ts`: `requestServiceEnrollment` (verify, ask must be askable, device code = 32 random bytes shown once, only its sha256 stored) and `pollServiceEnrollment` (RFC 8628 `authorization_pending` | `slow_down` | `access_denied` | `expired_token`; after the admin's yes, a PENDING key made by `mintKey` and SEALED as a compact JWE (ECDH-ES, A256GCM, `seal.ts`) to the token's `cnf.jwk`; the plaintext is the key; a repeat poll before confirm replaces the pending key; a confirmed key spends the code). `http.ts` is the one route contract (`requestServiceEnrollmentOperation`, `pollServiceEnrollmentOperation`, `enrollmentHttp`; every answer `no-store`). `postgres.ts` is the store (`createPostgresEnrollmentStore(client)`, a service-role `begin`-capable client, the same BYPASSRLS guard as the credential store; admission/service/user advisory locks serialize capacity writers so the caps hold: 5 open enrollments, 25 active and250 retained identities; expired operations free active capacity while identity and consent remain). `migrations/agent_service_enrollments.sql` is the migration template (table, `agent_principals.service_key`, the `service_enrollment` key origin and the trigger that kills a principal's sibling keys when an enrolled key is confirmed). CONFORMANCE: `@cogni-dao/agent-grants/enrollment-conformance` exports `runEnrollmentConformance(harness)`; the package runs it over a memory store, every adopting node MUST run the identical rows over its real SQL store (node-template: `app/tests/component/db/agent-service-enrollments.int.test.ts`). The `knowledge.read` route-only capability (scope `knowledge:read`, `serviceKeyedOnly`) gates ONLY a principal whose `agent_principals.service_key` is set (`isServicePrincipal` on the store): an existing agent key and a signed-in human read exactly as before; an enrolled service needs an approved role row (403 before the click, 200 after, 403 when Off).

- Provider foundation0043 is a required forward migration after immutable0041/0042: monotonic principal confirmation summary, compatible history reader, leased20-row non-destructive maintenance and bounded sibling retirement. `maintenanceTick` is exported from `/enrollment`; purge stays disabled until a separately proven serving-reader cutover. V2 receipt/requester custody is a separate approved implementation seam.

- `@cogni-dao/agent-grants/enrollment-client` (subpath, 0.4.0; REQUESTER half of the same protocol, one version with `./enrollment`) is what a service of one node (operator git-review) uses to ask another node for a key. PURE AND STORAGE-FREE: it imports only `jose`, `zod` and this package's pure `claims`, `seal`, `http` (wire zod shapes) and `credentials/key-format` modules, never `postgres`, `roles`, a store or a service, so a node that has not adopted grants needs only `fetch` and `jose` (`tests/enrollment-client-boundary.test.ts` walks the import graph and fails on any other edge). `sign.ts`: `buildEnrollmentClaims` + `createEnrollmentSigner({ kid, key } | { kid, signBytes })` (EdDSA, own `typ`/`kind`, checked against the provider's zod shape and the 10 minute cap before signing). `keypair.ts`: `generateLinkKeypair` (ephemeral X25519) and `unsealServiceKey` (ECDH-ES + A256GCM pinned, plaintext must be a well-formed revocable key). `transport.ts`: `createEnrollmentTransport({ fetch })` with `postEnrollment` / `pollToken` / `confirmKey` (https and the caller's origin only, `redirect: manual`, 10 s timeout, 64 KiB cap enforced while reading by `bounded-body.ts`, node-supplied interval and expiry clamped to 5..60 s and 60..86400 s, answers parsed with the provider's own `requestServiceEnrollmentOperation` / `pollServiceEnrollmentOperation`). `enroll.ts`: `startEnrollment` (hands back device code and private JWK for the CALLER to store), `pollEnrollment` (clamped loop, `slow_down` +5 s, transient retry, abort) and `enrollService` (whole handshake for a caller with nowhere to persist). The link table, the vault write of the key and the host-bound call transport stay in the app: storage differs per node. CONFORMANCE: `tests/enrollment-client.test.ts` runs the client against the provider in one process (real token verifier, memory store): enroll, 403 at the door before the click, On, poll, unseal, the key matches the provider's stored hash, confirm, a read passes the door, Off is 403.

- Every Postgres consumer (credentials-only included) must adopt the complete strict template chain in migrations/README.md through agent_authority_review_repairs.sql (reference0045), not just0039–0042. Package-only real-Postgres conformance qualifies this chain without node app migrations/seeds.
- maintenanceTick requires postgres.js-compatible cancellable pending queries; one cumulative2s budget includes lease, every query, final bookkeeping and remaining COMMIT allowance. Exhaustion cancels/rolls back and returns processed0/due=true. Maintenance tries authority locks in order and skips locked principal/receipt/role rows; ordinary authority writers retain their existing blocking order. No purge.

# agent-grants

Published `@cogni-dao/agent-grants` owns runtime tool authority: `authorize()`, role-row reads and writes, and `guardTools()` that wraps every tool runtime's `exec`.

- A tool runs only when its graph lock, principal lock and subject lock open. Read-only tools need only the graph lock. Design: https://cognidao.org/knowledge/node-capability-grants-standard (section "Runtime identity does not depend on hosting").
- No private `@cogni/*` import, no app ExecutionScope, no ai-core import. Runtimes are structural (`id`, `effect`, `exec`). The node passes `withStore`, `adminCheck`, `onDecision` and `runAs`.
- `/postgres` adapter (exported from the root) takes an injected tagged-template function. It never creates a client or switches a role. `agent_roles` has FORCE RLS and no policy, so only a service-role connection reads or writes it. `agent_principals` has a read-only select policy for every role (the wallet-binding trigger needs it); only a service-role connection writes it.
- A denial throws `ToolAuthorityError` with `receipt {code, retryable:false, lookup}`. The message is fixed and never names a role or scope.
- Every authenticated caller is the run subject, bearer agents included. A subject only narrows: `admin` means a principal the DAO approved; no AI identity is approved yet (item I2), so an agent fails `admin` tools, passes `member` tools, and `own` tools run on its own rows. Account scopes are out of scope: an `account` tool is denied with `policy_denied`.
- `node-ai.ts` builds the admin table rows (Who · Can do · Until · On), one per grant row, in three blocks (asks waiting, this node's AI, outside agents). Name and description come only from the declarations (`requires.label`, `requires.description`); NAMES_ARE_IDENTIFIERS: Who is this node's AI by its slug and an outside agent by its registered name (never a vanity label). There is no copy table and no display name.
- `roles.ts` holds the ask (`requestAccess`: a pending row, `approved_by` null, for the caller only) and the admin's yes (`grantRole`: approves a pending ask, or grants an internal AI directly), no (`denyRequest`) and take-back (`revokeRole`). LIVE_NEEDS_APPROVAL: `hasLiveRole` and `liveScopes` count only rows with an approver and no revoke, so a pending ask opens no lock.
- `same-door.ts` is SAME_DOOR: `SAME_DOOR_ROUTES` maps each write tool to the route ids that twin it, `ROUTE_ONLY_CAPABILITIES` declares routes no tool twins (`knowledge.contribute`, `work.item.review`: scope `work_item:review` on `POST /api/v1/work/items/{id}/artifacts`, task.0028), `NO_ROUTE_TWIN` allowlists tools with no node route, and `authorizeCaller()` is the route door (a bearer is its own principal and needs a live role row; a human session passes the subject rules). A parity test in `@cogni-dao/langgraph-graphs` fails on any unmapped write tool.
- DENIAL_IS_TERMINAL: `offeredToolIds()` drops tools whose principal lock already fails, and `guardTools` calls `onTerminalDenial` once per exec-time denial so the node ends the run cleanly.
- Roles are never cached. A revoked role denies the next call.
- Declared scopes live in the node, derived from the `requires` on its tool contracts. `grantRole` rejects an undeclared scope.
- Build declarations only with tsc; tsup owns JavaScript.
- `@cogni-dao/agent-grants/credentials` (subpath; a node adopts it alone) owns revocable hashed agent keys (key = `REVOCABLE_KEY_PREFIX` + 43 base64url chars of 32 random bytes + a 6-char base62 CRC32 checksum; `key-format.ts` is the one definition: `formatRevocableKey`, `isWellFormedRevocableKey`, `REVOCABLE_KEY_SCAN_PATTERN` for secret scanners; TOKEN_HASH_ONLY, the store sees sha256 of the whole token): `verifyBearer`, `upgradeSignedKey`, `rotateCredential`, `confirmCredential`, `revokeCredential` over a `CredentialStore` port plus the Postgres adapter (`createPostgresCredentialStore(client, { hasRoles })`, a service-role `begin`-capable client; `hasRoles` is the node's read of "does this principal hold roles": node-template passes `agentRolesHasRoles(client)`, the operator passes its OpenFGA read. Every store call first verifies once per instance that the role bypasses RLS (`rolbypassrls` or superuser) and otherwise throws, so a wrong role is 503, never a silent "never confirmed"). State (pending, active, renew_only, expired, revoked) is derived from timestamps by the SQL function `agent_credential_state`, read against the DATABASE clock; it is never stored. A store outage is `unavailable` (503), never `invalid` (401). Rotate supersedes a repeat call; confirm is idempotent and retires the predecessor in one transaction. `migrations/agent_credentials.sql` + README is the migration template (a node generates its own snapshot). The v1 HMAC verify stays in the node and is not touched; after it, the node calls `assertV1NotSuperseded` so a user with a CONFIRMED revocable key (revoked or not) can no longer use signed keys (`V1SupersededError`, 401 `v1_superseded`). Any store failure at any step surfaces as `CredentialStoreUnavailableError` (503). A token with the wrong shape or a failing checksum is refused before any store read; `verifyBearer(store, token, allow, { admit })` calls the node's per-IP `admit` after the shape check and before the store (over the limit = `rate_limited`, the node answers 429). BINDING_BEFORE_UPGRADE (roles and no GitHub binding = `binding_required`) runs at upgrade AND again at confirm for an upgrade key. CONFORMANCE (SUITE_GATES_RELEASE): `@cogni-dao/agent-grants/conformance` exports `runCredentialConformance(harness)`; the harness passes the test runner, creates users, moves timestamps and breaks the store. The package runs it over a memory store (`tests/credentials.test.ts`); every adopting node MUST run the identical rows over its real SQL store (node-template: `app/tests/component/db/agent-credentials.int.test.ts`).

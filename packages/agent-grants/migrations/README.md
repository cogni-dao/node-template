# Agent authority migration templates

Required reads: [service enrollment](https://node-template.cognidao.org/knowledge/node-service-enrollment), [agent key lifecycle](https://node-template.cognidao.org/knowledge/node-agent-key-lifecycle), and the [schema update contract](https://node-template.cognidao.org/knowledge/node-schema-update-contract).

Use the node's own schema and migration runner. Generate its DDL, journal and snapshot from its own predecessor; never copy another node's snapshot or rewrite exercised history. Append each template's custom SQL: guards, functions, triggers, RLS and transactional backfill cannot all be generated by Drizzle. Do not suppress predecessor-shape failures or weaken constraints. Run `db:check`; verify the journal timestamp follows prior entries. The foundation backfill runs under its mutation lock as table owner, temporarily lifts FORCE RLS and restores it before commit; a failure must roll back.

Authority hosts need `users(id text primary key, name text, wallet_address text)` and `user_bindings(user_id text -> users.id, provider text, external_id text)`, plus PostgreSQL `gen_random_uuid()`. Preserve existing identities, bindings, credentials and consent. Authority writes need a BYPASSRLS service connection; protected tables have ENABLE and FORCE RLS and no app policy.

Apply these templates once, in order, through the adopter's journal:

| Stage | Required predecessor |
| --- | --- |
| `agent_authority.sql` | Host prerequisites; skip only if its exact authority baseline exists. |
| `agent_credentials.sql` | Authority baseline. |
| `agent_service_enrollments.sql` | Credential baseline; also required for credentials-only adopters. |
| `agent_service_enrollment_maintenance.sql` | Enrollment baseline. |
| `agent_authority_foundation.sql` | All preceding stages; includes transactional backfill. |
| `agent_authority_guard_compatibility.sql` | Foundation. |
| `agent_authority_review_repairs.sql` | Guard compatibility. |
| `agent_authority_maintenance_cursor.sql` | Review repairs. |
| `agent_authority_v2_reader.sql` | Maintenance cursor; also required for authority-only readers. |
| `agent_authority_consent_control.sql` | V2 reader; generated consent-control index. |

For an existing 0036-only authority, apply `agent_access_requests.sql` before credentials instead of replaying `agent_authority.sql`. Other existing adopters start after their last verified predecessor; do not replay baselines. Credentials-only adopters at 0039/0040 need enrollment and all subsequent authority stages; adopters at 0045 need the cursor, v2 reader and consent-control stages. Verify the actual predecessor shape before applying a stage.

**Full provider and requester:** after the authority chain, apply `agent_service_enrollment_v2.sql`, then `agent_service_enrollment_review_guards.sql`, then `agent_service_enrollment_consent_expiry.sql`, then `agent_service_enrollment_audit.sql` (reference 0050). These require the host's `billing_accounts` and `connections` schemas; adapt the connection DDL and generate the host's own migration. Do not replay v2 when applying later guards. For unbackfilled legacy identities, supply reviewed `{home,services}` mappings through `createPostgresEnrollmentStore(client, {legacyHomes})`; node-template's trusted-home configuration uses `reconcileLegacy: true`. Missing or ambiguous mappings must fail closed; preserve existing markers, users and consent.

**Requester-only host:** apply `agent_service_requester.sql` against the host's `billing_accounts` and `connections` instead of the authority/full-provider chain. Then apply `agent_service_requester_audit.sql`; it reuses only the existing rollout-state singleton, without provider tables. Do not apply both alternative template chains to the same operations table. Call `requesterMaintenanceTick(client)` from the host's existing maintenance driver. A full provider calls `maintainRequesterCustody(tx)` and `maintainEnrollmentDelivery(tx)` inside its existing `maintenanceTick` callback; the package shares that transaction's row budget.

The adapter requires a begin-capable postgres.js-compatible client; `maintenanceTick` also requires cancellable pending queries (`PendingQuery.cancel()`). Keep its cumulative two-second transaction budget and rollback on exhaustion. Verify columns, indexes, constraints, trigger definitions, FORCE RLS, migration receipt and `backfill_ready=true` where the authority foundation applies. Both audit stages leave purge disabled. Enable the database flag only after complete backfill and qualification of every serving reader at the recorded minimum reader build; do not roll back below that build while purge is enabled. Validate the package templates with the adopter's migration owner, ordinary app role and BYPASSRLS service role; a reference-node migration is not an adopter receipt.
